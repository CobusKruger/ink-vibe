# WP/FSE Buildability Review — ink-vibe

_Lens: WordPress 7.0+ FSE block-theme buildability of the theme visual-fidelity spec (`theme-fidelity-spec.md`). No files changed. Cross-checked against `theme.json` (v3), `functions.php`, `templates/front-page.html`, `patterns/*`, `ink-core` dynamic blocks (`FeaturedWinners`, `HomepageStrip`), and the three-layer rules in `project-context.md`._

## Overall verdict

**Buildable — with three real friction points that must be resolved into the stories before build, and two that are cross-layer (ink-core) not pure-theme.** The spec is technically sound and refreshingly WP-aware: it already routes dynamic data to `ink-core` (never asks the theme to hold business logic), recommends the correct asset-enqueue mechanism, and its token discipline matches the codebase. Nothing in it is *infeasible* on WP 7.0+. But four mechanisms are more awkward than the spec implies and will hit a wall if a story assumes the naive path: (1) **button size as a block style** — block styles are a single radio-select axis and cannot cleanly express size × variant; (2) **icons inside `core/button`** — core has no icon support, and the theme currently ships *no icon system at all*; (3) the **rich winner card visual (§5) is coupled to `ink-core` block output**, not stylable from the theme; and (4) **core/columns' stack breakpoint is fixed (~782px), not the spec's 1024px**. The home-CSS-layer prerequisite is correctly identified and correctly sequenced first. Recommend accepting the spec with the story-slicing adjustments below (split presentation from data-wiring; pre-land the two `ink-core` seams).

## Findings

- **[high]** The rich winner card visual (gold gradient, Crown watermark, 48px avatar, italic Lora quote, per-rank label) **cannot be produced by the theme** — it is coupled to what `ink/wenner-kollig` emits, and that block (`FeaturedWinners::toHtml()`) currently outputs only a flat `<h2>` + `<ul>/<li>` of `ink-wenner-kollig__*` list rows with no avatar, quote, watermark, or card structure. Theme CSS over that markup can restyle the list but cannot invent an avatar/quote/crown DOM (§5). *Fix/approach:* treat §5 fidelity as an `ink-core` change (Epic 12A) — upgrade the block's `render`/`toHtml` to emit the card DOM (avatar, `<blockquote>`, rank label paired with text+icon, gold token classes), keeping the pure-`toHtml` + `FEATURED_FILTER` seam it already has; the theme then supplies only token-driven styling in `home.css`. Do **not** try to satisfy §5 purely in the theme.

- **[high]** Every button in the design carries a Lucide icon (BookOpen, arrow, PenLine, Sparkles, Crown, Trophy, Calendar, Users, Clock, Heart, MessageCircle) but **`core/button` has no icon support and the theme ships no icon system** (`grep` finds zero inline `<svg>` in `patterns/` and no icon block registered) (§2, §3, §5, §8, §9). *Fix/approach:* establish an inline-SVG icon convention as part of 19-1: icons that live inside **static locked patterns** are hand-placed inline `<svg>` (token `currentColor` fill, `size-4`=16px) inside the button's flex row, or via a `::before` `mask-image` utility class in `home.css`; icons inside **dynamic sections** (winner card, challenge card, featured counts) are emitted by the `ink-core` block PHP. Flag as a cross-cutting asset dependency, not a per-section detail.

- **[high]** Button **size** (sm/default/lg/xl) is not expressible as a block style. `register_block_style` adds one `is-style-*` class that the editor treats as a single radio-select axis, so you cannot combine `is-style-ink-primary` (variant) with a separate size style on the same button (§0.1, §9). Also note "height" is not a button property — 44/48px come from padding + line-height, not a `height`. *Fix/approach:* keep **variant** as the block style (color/border/font treatment, incl. `:hover` via `inline_style`), and set **size** per-instance in the locked pattern markup via `core/button`'s spacing/typography supports referencing tokens (`px`→`s-*`, font-size preset, `min-height` via style) — the home sections are locked patterns, so baking size per-instance is clean and avoids a utility-class matrix. If a site-wide reusable sized button is later wanted, add `ink-btn-sm/lg/xl` utility classes in `home.css` and type them into the Advanced → CSS-class field.

- **[medium]** `core/columns` stacks at a **fixed breakpoint (~782px, `stackOnMobile`)** that is not configurable to the spec's 1024px hero split or 768px featured-grid split (§2, §6). The 50/50 two-column hero and the "single column < 1024px" rule will not stack where specced with plain columns. *Fix/approach:* use the **`core/group` Grid layout variation** (WP 6.3+) with `minimumColumnWidth` / explicit column spans, or drive the stack with a media query in `home.css` on the section's own class. Prefer Grid layout for the asymmetric featured grid; for the hero, a `home.css` `@media (max-width:1023px)` rule on the hero group is the reliable path. Do not rely on `core/columns` stack timing.

- **[medium]** The **asymmetric featured grid** (one full-width featured card spanning both columns + a 2-col grid of the rest) is not achievable with `core/columns` (§6). *Fix/approach:* use `core/group` **Grid layout** with per-child `columnSpan` (the featured child spans 2), WP 6.3+ — this is the native mechanism for span-based asymmetry. Wire the cards themselves with a `core/query` loop over the ink CPTs *or* an `ink-core` featured-stream block (see next finding).

- **[medium]** `background-clip:text` gradient heading (§0.3) is not expressible via `theme.json` and is **awkward as an editor block style**, because the accent is a *sub-phrase inside a heading* and FSE cannot apply a block style to part of a heading's rich text. *Fix/approach:* in the locked hero pattern, split the accent phrase into its own inline element with a utility class (`.ink-text-gradient`) styled in `home.css` (`background:linear-gradient(...);-webkit-background-clip:text;background-clip:text;color:transparent`); wrap in `@supports` with a solid `primary` fallback. This is pattern markup + CSS, not an editor-friendly toggle — acceptable because the hero is locked.

- **[medium]** Alpha tints via `hsl(var(--…) / a)` are **not viable** as written, because the palette tokens are opaque hex (`#EA4015` etc.), so `hsl()`/`rgb()` cannot read channels off them (token-mapping note 2). *Fix/approach:* standardise on **`color-mix(in srgb, var(--wp--preset--color--primary) 10%, transparent)`** (Chrome 111+/Safari 16.2+/FF 113+ — universally available by 2026), and declare an opaque fallback property first for old engines. Drop the `hsl(var/a)` alternative from the spec — it would require adding parallel HSL-channel custom properties, which is not worth it.

- **[medium]** No **home CSS layer exists**: `grep` confirms zero `wp_enqueue_style` / `add_editor_style` in the theme, and `style.css` is not enqueued. §0.3–0.6 (gradient text, plus-pattern, hover-lift, keyframes, reduced-motion) all depend on it (§0 note). *Fix/approach:* the spec's recommendation is correct — add a versioned `wp_enqueue_style('ink-foundation-home', get_theme_file_uri('assets/css/home.css'), [], $theme->get('Version'))` gated to the front page, mirroring the existing `wp_enqueue_script` pattern in `functions.php` (per the asset-enqueue rule; keeps `theme.json` lean). This is load-bearing and correctly slotted into 19-1 first. Minor correction to the §0.5/§0.6 rationale: block styles' `inline_style` **can** contain `:hover` and `@keyframes` (it is raw CSS — the existing `theme.json` `css` string already ships an `:hover` rule), so "block styles alone can't do hover/keyframes" is imprecise; the enqueued `home.css` is still the better mechanism for the volume of home CSS.

- **[medium]** The **current-uitdaging card (§3)** needs a live per-challenge data surface that does not exist — today's `huidige-uitdaging.php` is explicitly static ("dra geen per-uitdaging-logika"), and the dynamic surface is deferred to Epic 12/12A (§3, §11). Building §3's card presentation against nothing risks shipping a static teaser dressed as a live card. *Fix/approach:* add an `ink-core` dynamic block (e.g. `ink/huidige-uitdaging`) following the established house style — thin `render` + pure `toHtml` + a data seam + graceful collapse (exactly like `FeaturedWinners`/`HomepageStrip`). The theme embeds the block and styles it; the query for the open `uitdaging` (title/prompt/deadline) lives in `ink-core`.

- **[medium]** **Featured bydraes (§6)** and the **stats row (§4)** need data the theme cannot supply, and two sub-decisions have a three-layer trap: read-time "compute from word count" (§6) and stats counts (§4) **must not be computed in the theme/pattern** (§6, §4, §11). *Fix/approach:* featured stream → `core/query` loop over gedig/storie/artikel *or* an `ink-core` featured-stream block; engagement counts (Heart/MessageCircle) and read-time are `ink-core`-owned values surfaced via block bindings or the block's own render — never a template calculation. Stats counts → `ink-core` provider, or an owner decision to ship static-at-launch with a copy-debt marker. The spec's §11 table already locates all of these correctly; just make the "no theme-side computation" constraint explicit in the story ACs.

- **[low]** Type ramp + fluid clamp (§0.2) is fully feasible: `theme.json` v3 already has `typography.fluid:true` and per-preset `fluid:{min,max}` (used on 2xl/3xl), and a literal `clamp()` string is a valid `size` — no WP-version constraint (fluid since 6.1). *Fix/approach:* add `4xl`/`5xl` presets and a `hero` fluid preset as specced. Note "hero-display typography role" is design vocabulary — in WP it resolves to a fontSize preset + an element/block-style applying Lora/600/1.25; there is no first-class "role" concept, so express it as preset + style.

- **[low]** Plus-pattern SVG texture (§0.4) is feasible and the `::before` overlay approach is the right FSE choice (a real `background-image` support at 0.03 opacity behind content is clumsier). *Fix/approach:* store the data-URI as a `settings.custom` value (emits `--wp--custom--ink--pattern--plus`) or inline it in `home.css`; apply via a `.ink-hero-texture::before` layer with `position:absolute;inset:0;opacity:.03;z-index:0;pointer-events:none` and content above at `z-index:1`. `pointer-events`/`z-index` are unconstrained in CSS.

- **[low]** `styles.elements.button` (§0.1) is fully supported in `theme.json` v3 (border.radius, background, color, typography, and `:hover`), and `register_block_style` on `core/button` with `inline_style` targeting `.wp-block-button.is-style-…__link` is exactly how the existing `is-style-pill` works — so the resting-and-hover *color/border/radius* treatments are straightforward. Default (no-style) de-pilling via `elements.button.border.radius` is correct. No issue beyond the size/icon findings above.

- **[low]** Block-locking for non-technical staff (§2, §6, §7) is already the codebase idiom (`lock:{move,remove}` throughout the templates/patterns). *Fix/approach:* for the assembled home sections, add `templateLock:"contentOnly"` on the section groups so staff can edit text/links but not restructure — this satisfies the project rule ("lock critical structure, keep content editable") more precisely than `lock:{move,remove}` alone.

- **[low]** Borg strip (§7) needs no new mechanism — `ink/borg-strook`/`HomepageStrip` already collapses correctly with no active sponsor, which the spec acknowledges. Sponsor-chip `hover:scale-105` is a `home.css` `:hover transform` (respect `prefers-reduced-motion`).

## Story-slicing assessment (19-1..19-5)

- **[medium]** Ordering is sound (foundations first, then hero, cards, featured, polish) and the home-CSS mechanism is correctly front-loaded into 19-1 — everything downstream depends on it. **But the "Data (parallel/prereq)" line under-specifies a hard dependency:** 19-3 (winner card §5) and 19-4 (featured stream §6) cannot reach their "real data" ACs until the `ink-core` seams land — and §5 in particular requires the `ink/wenner-kollig` *markup* to be upgraded (an Epic 12A change, cross-epic). If the card stories run before the providers, they will complete against graceful-collapse and quietly ship no live data. *Fix/approach:* split each dynamic section into (a) a presentation/markup story that builds against the collapsing block, and (b) a data-wiring story gated on the `ink-core` provider; or sequence the provider *within* the same story ahead of the card wiring. Make the 12/12A dependency for §3 (current-uitdaging block) and §5 (winner-card markup) explicit as blockers, not parallel work.
- **[low]** 19-1 correctly bundles the button primitive + type ramp + CSS mechanism; recommend it also lands the **icon convention** (finding above) and the **`color-mix` tint convention**, since §2 onward assume both exist.
