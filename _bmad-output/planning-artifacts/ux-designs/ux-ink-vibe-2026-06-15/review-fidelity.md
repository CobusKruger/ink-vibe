# Fidelity & Traceability Review — ink-vibe

Lens: Fidelity & Traceability (adversarial). Scope: `theme-fidelity-spec.md` verified value-by-value against the Lovable source of truth (`/Users/cobus/Development/ink-lovable` @ `5618f39`), the current theme (`wp-content/themes/ink-foundation/`), and `ink-core`. No files were changed.

## Overall verdict

**Accept with fixes.** The spec is unusually faithful. I spot-checked ~70 discrete values across all eight home sections plus the shared button/card/pill primitives; the overwhelming majority are correct to the pixel/token and cite the right source. The §9 button table, the hero (§2), the hero challenge card (§3), the stats row (§4), the winner + uitdaging feature cards (§5), the featured-works asymmetric grid (§6), and the CTA band (§8) are all accurate against `button.tsx`, `HeroSpotlight.tsx`, `ChallengeSection.tsx`, `FeaturedWorks.tsx`, and `CallToAction.tsx`. Every "current gap" claim I checked matches the actual theme code, and the §11 dynamic-data honesty is sound (the winner slot really is a wired-but-empty seam; the featured grid really is three hardcoded `Titel van die werk` placeholders). Copy discipline is strong — English strings are explicitly routed to `ui-copy-translations.md` / migrated DB and the "501(c)(3)" placeholder is explicitly flagged for discard.

The blocking issues are all in the **token layer**, not the pixel layer: one HIGH (the gold-token family the winner card depends on does not exist in `theme.json`, and the gold gradient can't be built from what does), plus three MEDIUM token-discipline / a11y-completeness gaps. None invalidate the spec; they need closing before Epic 19 build.

Counts: **0 critical · 1 high · 3 medium · 5 low.**

## Findings

### High

- **[high]** The winner-card gold gradient cannot be reproduced from tokens, and the spec misstates the token inventory. Open-Decision #1 says *"theme.json has `warning` (#D4A418), `gold-muted` (#C9B88A), and `goud` (= gold-muted)"* and §5 AC says *"map 'gold' moments to the `goud`/`gold-muted` token family"* — but **`theme.json` has no `goud` slug** (only `gold-muted` #C9B88A and `warning` #D4A418; the `brons`/`silwer`/`goud` `[NEW]` tokens in DESIGN.md were never propagated to the palette). More importantly, the Lovable winner card is a *two-stop* gradient `gold/10 → gold-muted/20` (`ChallengeSection.tsx:48`, bright gold `--gold: 42 80% 55%` ≈ #e8b130 → muted gold), and the *only* gold token in `theme.json` is the muted one — so the recommendation to add "no new bright-gold token" (Open Decision #1) makes the defining gradient collapse to near-flat. (spec §5 AC + Open Decision #1 vs `theme.json:24` palette + `ink-lovable/src/index.css:50-51` + `ChallengeSection.tsx:48`). *Fix:* either add a `goud`/`gold` opaque preset to `theme.json` (bright gold for the top stop) and reference it, or explicitly resolve the gradient to `gold-muted` + `warning` as the two stops; and correct the note so it stops asserting `goud` already exists in `theme.json`.

### Medium

- **[medium]** Primary-button shadow is mapped to the wrong token. The Lovable `literary` variant uses `shadow-soft` = `0 4px 20px -4px hsl(220 20% 12% / .08)` (`button.tsx:19` + `index.css:60`), which is **`theme.json` shadow preset `md`** (`theme.json:117`) — but §0.1's block-style AC and the §9 variant table both specify **`shadow-sm`** for `is-style-ink-primary`. `shadow-sm` is the *card* shadow (`0 2px 12px`, `theme.json:116` = Lovable `shadow-card`), which is visibly flatter. (spec §0.1 AC + §9 table vs `button.tsx:19` / `index.css:60` / `theme.json:116-117`). *Fix:* change the primary-button shadow reference from `shadow-sm` to `shadow-md` in both §0.1 and §9. (The §0.1 target prose already correctly says "shadow-soft" — only the WP-target mappings are wrong, so it is also internally inconsistent.)

- **[medium]** The spec hardcodes white button text/fill, contradicting its own no-hardcode-hex rule. The preamble bolds *"do not hardcode hex"*, yet §0.1 AC says button `text #fff`, §9 says "white text", and §8 says primary CTA is "white fill / terracotta text". `theme.json` has **no pure-white token** (closest is `surface-alt` #FDFCFA, which DESIGN.md `components.button-primary.color` already designates, and which the current patterns use). Lovable's `primary-foreground` is `0 0% 100%` (`index.css:11`), so #fff is faithful to Lovable but not to the theme's token system. (spec §0.1/§8/§9 vs `theme.json` palette + DESIGN.md `components.button-primary`). *Fix:* route "white" to a token — either `surface-alt` (matches existing convention) or add a named `white`/`on-primary` preset — rather than literal `#fff`.

- **[medium]** No acceptance criteria for focus states anywhere in the spec. Every Lovable interactive control carries `focus-visible:outline-none focus-visible:ring-2 focus-visible:ring-ring focus-visible:ring-offset-2` (`button.tsx:8`), and EXPERIENCE.md's Accessibility Floor explicitly requires *"visible focus states"*. The spec meticulously specs hover states (buttons, cards, nav, sponsor chips) but omits focus rings for buttons and links entirely. (spec §0/§1/§9 vs `button.tsx:8` + EXPERIENCE.md → Accessibility Floor). *Fix:* add an AC to §0.1/§9 for a visible focus-ring on buttons and nav links (2px `primary` ring + offset), and note reduced-motion already handled in §0.6.

### Low

- **[low]** The root-cause phrasing "buttons fall to WP core defaults → full-pill radius" (§0.1) is imprecise. WP core's `wp-element-button` default is not a 9999px pill; a missing `styles.elements.button` yields core's slightly-rounded default, not a lozenge. The observed pill in `design-staging.png` (which I could not open in this pass) may come from elsewhere. The prescribed fix (add `elements.button` + block styles) is still correct. (spec §0.1). *Fix:* soften to "buttons fall to core defaults (wrong radius/colour/typeface)"; confirm the pill symptom's actual source before asserting it.

- **[low]** Type-ramp low-end drift. `theme.json` `3xl` = `2rem`/32px (`theme.json:109`), but Lovable `text-3xl` = 30px. §0.2 correctly notes the 32px cap, but its generalization "Section titles `text-3xl → md:text-4xl` = 30 → 36px" only holds if a true 30px step is used; section titles mapped onto the existing `3xl`→`4xl` render **32 → 36**, not 30 → 36. The hero fluid `clamp(30 → 48)` sidesteps this. (spec §0.2 vs `theme.json:109` + `FeaturedWorks.tsx:61`). *Fix:* either accept 32px as the section-title low end or add a 30px step; note the 2px difference explicitly.

- **[low]** The stats values `12K+ / 48K+ / 150K+` (§4) are Lovable fabrications (`HeroSpotlight.tsx:136-145`). §4 rightly flags the real-vs-static data decision, but the AC still lists the placeholder numbers; if built static-at-launch they must not be presented as real counts. (spec §4 vs `HeroSpotlight.tsx:136-145`). *Fix:* mark the numbers as placeholder-only and tie shipping them to the §11/Open-Decision data decision + copy-debt.

- **[low]** §7 (Borg strip) is materially under-specified versus its source. `SponsorsSection.tsx:31-48` has precise per-tier chip styling (gold `bg-gold/10 border-gold/20`; silver `bg-secondary border`; bronze `bg-muted/50`), chip metrics (`px-6 py-3 rounded-lg`, `text-lg`/`text-base`), and an intro paragraph — none captured; §7 only says "chips with tier styling + `hover:scale-105`". This is less testable than every sibling section. Partly justified because the strip is dynamic/collapsing, but the tier-chip appearance is still a fidelity target. (spec §7 vs `SponsorsSection.tsx:31-48`). *Fix:* add the per-tier chip token mapping + chip metrics as ACs.

- **[low]** Logo feather icon not required by any AC. Lovable's logo is `Feather` icon (24px terracotta) + wordmark (`Header.tsx:33`); the current theme uses a bare `core/site-title` (no icon, weight 700 vs Lovable 600). §1's *target* mentions the feather, but no §1 AC requires adding it, so it could silently ship iconless. (spec §1 AC vs `Header.tsx:33-36` + `header-main.php:13`). *Fix:* add an AC for the feather glyph + confirm wordmark weight 600.
